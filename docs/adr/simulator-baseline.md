# Simulator baseline and regression gate (MSH-27)

Status: accepted.

## Context

MSH-08 to MSH-11 carry quantitative targets, and later milestones must be
compared against a stable baseline. Ad-hoc unit tests prove single-hop rules
but cannot measure delivery under mobility, topology churn or queue pressure.

## Decision

Use aoNetwork's paused `SimWorld` and drive the real `NetworkAdapter` with
signed `MeshHello`s, transport events and the sans-IO engine. The harness is
host-side only, behind feature `sim`; the core gains no clock, I/O or runtime
dependency. The two narrow adapter accessors (`engine_mut`, `network_mut`)
let the harness count engine outputs before the adapter applies them, so one
broadcast is counted per up link without a second source of truth.

Four fixed scenarios span the required models: a 20-node line, a 50-node
random-waypoint graph, a 100-node community graph and a 200-node chain with
scripted shortcut contacts. Seeds drive positions, connect jitter, identities,
traffic and sealing streams through small deterministic generators. Every
submitted Direct message targets a node two to eight hops away along the
line, so the baseline measures forwarding rather than expiry at an impossible
graph distance. Submissions are spread across the first four fifths of the
run, leaving a drain tail; otherwise the last message is cut off by the clock
and scripted contacts fire after all traffic has ended. The scripted scenario
actually toggles its shortcut ranges at their recorded run-relative times. The
lossy mobile scenarios are retained as the baseline that spray-and-wait and
sync work must improve.

Metrics are delivery ratio, mean and maximum latency, overhead (transmissions
per delivery), duplicate ratio, radio bytes and peak queue occupancy. Because
the consumed aoNetwork exposes per-link `tx_bytes` but not the queue itself,
the harness tracks enqueued bytes per link and retires them as the radio
counter advances; a link that closes drops its remaining bytes. Queue baselines
are taken after settlement, so hello traffic is excluded. Radio bytes are the
sum of per-tick `tx_bytes` deltas after settlement, kept per link even after it
closes; subtracting two snapshots of only the currently up links would invent
or lose bytes whenever mobility changes the neighbour set.

The CSV report is generated by `cargo run --release --features sim --example
sim_report`. `tests/sim_baseline.rs` and `.github/workflows/sim.yml` enforce
directional bounds: higher delivery is good, lower overhead, latency,
duplicates, radio bytes and peak occupancy are good. A legitimate improvement
passes; a regression fails without editing the constants.

The fixture was refreshed after aoNetwork `492e148c` (Net 25 flow control)
changed simulated link formation. The seeds and scenarios are unchanged;
waypoint and community delivery improved, waypoint overhead fell, and
community overhead rose slightly from 328.5541 to 328.7067. Both exact link
counts were rerecorded. Radio-byte accounting was corrected to accumulate
per-tick deltas per link, so the higher figures include traffic on links that
close during mobility rather than losing it at a snapshot boundary. Repeated
debug and release runs produced identical metrics; the README table carries
the regenerated values.

## Alternatives considered

- **Extend the existing forwarding unit tests with topology assertions.**
  Rejected: they use a stub transport and cannot represent hello timing,
  mobility or radio queueing, so the numbers would not transfer to the real
  network layer.
- **Write a purpose-built mesh-only fake network.** Rejected: it would
  duplicate aoNetwork's link state and could silently diverge from the
  transport the engine actually consumes. NET-09 owns the simulator.
- **Seed CI from the wall clock and record whatever it gets.** Rejected: the
  baseline would not be reproducible and a regression could be hidden by a
  lucky seed.

## Published measurement

Release profile, stable Rust, fixed seeds from `baseline_scenarios()`:

| Scenario | Seed | Delivered / submitted | Delivery ratio | Overhead | Mean / max latency (ms) | Radio bytes | Peak queued bytes |
|---|---:|---:|---:|---:|---:|---:|---:|
| `line-20` | 1297303584 | 20 / 20 | 1.0000 | 9.6500 | 727 / 1200 | 102065 | 550 |
| `waypoint-50` | 1297303632 | 31 / 50 | 0.6200 | 125.7742 | 551 / 1200 | 2080893 | 12375 |
| `community-100` | 1297303652 | 75 / 80 | 0.9375 | 328.7067 | 676 / 1200 | 13031341 | 33290 |
| `scripted-200` | 1297303752 | 100 / 100 | 1.0000 | 34.5500 | 561 / 1200 | 1850727 | 6600 |

Every scenario has zero send failures and zero duplicate deliveries. These are
the rows carried by the `v0.1.0` tag and by the README; a
`release_docs::published_baseline_matches_readme_and_adr` test keeps the three
copies identical. Regenerate them with
`cargo run --release --features sim --example sim_report -- baselines.csv`.

MSH-19 adds one separate scenario rather than changing the four gates above.
`presence_scenarios()` uses seed `1297304021` on a static 50-node circulant
(steps 1, 8 and 12), submits no application messages, and declares every card
hash up front. The fixed report learns 49 of 49 peers in 50 ms, emits zero
`CardFetch` events, and sends 6,036 announcement frames (1,557,288 bytes) in
the last 60 seconds. `tests/sim_presence.rs` locks the exact CSV header and
row; `cargo run --release --features sim --example presence_report` reproduces
it. Presence is disabled in all four baseline scenarios, so their rows stay
comparable.

## Consequences

- Any routing, codec or adapter change that affects these numbers must be
  measured with the same command and the new numbers recorded in the PR and
  README.
- Thresholds are never lowered merely to make CI pass.
- Sibling changes to aoNetwork's simulator can move the baseline; land them
  first and republish it in a separate, reviewed change.
